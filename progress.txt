## Codebase Patterns
- The php container sets `APP_ENV=dev` as a real OS environment variable
  (docker-compose.yml), which takes precedence over phpunit.dist.xml's
  `<server name="APP_ENV" value="test" force="true"/>`. Run tests with
  `docker compose exec -e APP_ENV=test php bin/phpunit` (or
  `bin/console ... --env=test` for console commands against the test DB).
- `php:8.5-fpm` already ships PDO core and Zend OPcache built in — only run
  `docker-php-ext-install pdo_pgsql intl zip` (NOT `pdo` or `opcache`, those
  fail with "cannot stat 'modules/*'" since they have no separate .so to copy).
- backend/ is the Symfony app root (served via nginx from backend/public),
  frontend/ is the Vite/React app root. Both are bind-mounted into their
  containers so host edits are picked up live.
- docker-compose.yml uses `${VAR:-default}` everywhere so the stack works
  out of the box even without a `.env` file; `.env.example` documents all
  overridable vars (DB creds, JWT key paths, CORS origin, ports, app URL).
- frontend/ is a Vite + React 18 + TypeScript app. To add a new frontend
  dependency: edit frontend/package.json, run `docker compose exec node npm
  install`, then `docker run --rm -v "$(pwd)/frontend:/app" alpine chown -R
  1000:1000 /app` to fix root ownership of node_modules/package-lock.json
  before editing with host tools, then `docker compose restart node` to pick
  up the new vite.config.ts/deps. Run `docker compose exec node npm run
  typecheck` (= `tsc --noEmit`) before committing.
- Tailwind CSS v4 is wired via the `@tailwindcss/vite` plugin (in
  vite.config.ts) — no postcss.config/tailwind.config files needed;
  frontend/src/index.css just contains `@import "tailwindcss";`.
- security.yaml `access_control` is first-match-wins: any new path-specific
  rule (e.g. an admin-only attribute backed by a custom Voter) must be listed
  ABOVE the generic `^/api -> IS_AUTHENTICATED_FULLY` catch-all, or it will
  never be reached.
- Voter classes under src/Security/Voter/ extending Symfony's `Voter` are
  auto-registered as `security.voter` services via autoconfigure - no manual
  service tagging needed.
- For entity properties exposed via API Platform where a getter returns a
  different shape than the underlying Doctrine association (e.g. User::$roles
  is `Collection<Role>` but `getRoles(): array<string>` per UserInterface),
  add `#[Ignore]` (Symfony\Component\Serializer\Attribute\Ignore) to the
  property to avoid "Unexpected non-object element in to-many relation"
  normalizer errors; expose the desired shape under a different field name
  if needed.
- API Platform write pattern for entities needing custom field mapping
  (e.g. plain-text password -> hash, role codes -> Role entities): give the
  Post/Patch operation an `input: SomeInput::class` DTO (plain class with
  public properties, optionally `#[Assert\*]` constraints - API Platform
  validates the DTO automatically) and a `processor: SomeProcessor::class`
  implementing `ApiPlatform\State\ProcessorInterface`. The processor calls
  a dedicated `*Service` (thick service / thin processor) that does the
  mapping + EntityManager persist/flush. For Patch, do NOT rely on
  `$context['previous_data']` as the entity to mutate - it is NOT a
  UnitOfWork-managed instance (flush() silently no-ops on it); instead
  re-fetch the entity via its repository using `$uriVariables['id']` inside
  the processor. For business-rule rejections (e.g. "can't delete your own
  account"), throw `Symfony\Component\HttpKernel\Exception\ConflictHttpException`
  with a Polish message - API Platform returns it as a 409 with that message
  in `detail`.
- For DTO field constraints that need a DB lookup (e.g. "code must be
  unique" on a plain input DTO with no Doctrine UniqueEntity support), write
  a custom `Symfony\Component\Validator\Constraint` +
  `ConstraintValidator` pair under src/Validator/ (validator constructor can
  inject a repository directly - validators are services). Apply it as an
  attribute on the DTO property alongside `Assert\NotBlank`/`Assert\Regex`
  etc. API Platform's automatic DTO validation runs all of these together and
  returns a single 422 `ConstraintViolation` response with a `violations`
  array (each entry has `propertyPath` + `message`) - no manual
  ValidationException handling needed in the processor/service.
- When exposing a `Collection<Entity>` association as `list<string>` via a
  getter (e.g. `array_map(fn(Role $r) => $r->getCode(), $collection->toArray())`),
  always wrap the result in `array_values()`. After `removeElement()` +
  `add()` on a Doctrine `ArrayCollection`, `toArray()` can return
  non-sequential integer keys; `array_map` preserves those keys, and
  `json_encode` then serializes the result as a JSON *object*
  (`{"1":"X","2":"Y"}`) instead of an array, breaking frontend code expecting
  `string[]`.
- frontend/CLAUDE.md documents `getCurrentUser()`/`hasRole()` (JWT payload
  decoding) and `<RequireAdmin>` for admin-only routes, plus the
  `application/merge-patch+json` Content-Type requirement for PATCH via
  apiFetch - read it before building more admin panels or PATCH calls.
- For an input DTO field that's an IRI reference to another resource (e.g.
  Employee's `company`), validate it with a custom Constraint +
  ConstraintValidator (e.g. ValidCompanyReference) that injects
  `ApiPlatform\Metadata\IriConverterInterface` and calls
  `getResourceFromIri($value)` in a try/catch for
  `ApiPlatform\Metadata\Exception\InvalidArgumentException` /
  `ItemNotFoundException`, adding a Polish violation on that property if it
  throws or returns the wrong entity type. The Create/Update processors then
  call `getResourceFromIri()` again (validation already guarantees success,
  so just `\assert($x instanceof TargetEntity)`) to get the entity to pass
  into the *Service. Reusable for US-021 (Referral's `employee` and each
  ReferralExposureFactor's `factor` IRI).
- To get the authenticated user as an `App\Entity\User` inside a Create
  processor (e.g. for a `createdBy` field), inject
  `Symfony\Bundle\SecurityBundle\Security` and call `->getUser()`, then
  `\assert($user instanceof User)`.
- A service that needs a "reject delete if referenced elsewhere" 409 guard
  (e.g. CompanyService::deleteCompany checking for linked Employees) just
  injects the other entity's repository and calls
  `$repository->count(['<association>' => $entity]) > 0`, throwing
  `ConflictHttpException` with a Polish message before remove()+flush(). Same
  pattern will apply to ExposureFactorService::delete (US-018/US-020) checking
  ReferralExposureFactor references.
- API Platform's default route path for a multi-word entity (e.g.
  ExposureCategory) is snake_case (`/api/exposure_categories`), not the
  kebab-case the PRD's AC literally specifies (`/api/exposure-categories`).
  When an AC gives an exact kebab-case path, set an explicit `uriTemplate` on
  every operation: `new GetCollection(uriTemplate: '/exposure-categories')`,
  `new Get(uriTemplate: '/exposure-categories/{id}')`,
  `new Post(uriTemplate: '/exposure-factors', ...)`,
  `new Delete(uriTemplate: '/exposure-factors/{id}', ...)`. Verify with
  `bin/console debug:router | grep <name>`.
- To expose a Doctrine OneToMany inverse-side collection as *nested embedded
  data* (not an array of IRIs) - e.g. ExposureCategory#getFactors() returning
  each ExposureFactor's {id, name, description} inline in
  GET /api/exposure-categories - mark the `Collection<Entity>` property
  `#[Ignore]` and add a separate getter that maps the collection to plain PHP
  arrays (not entity objects); the serializer then emits nested JSON objects
  directly with no IRI conversion. The owning ManyToOne side must add
  `inversedBy: 'theCollectionProperty'` or
  `doctrine:schema:validate` fails ("inverse side ... does not contain the
  required inversedBy attribute") even though no DB column changes.
- For an entity field backed by a fixed set of string values (e.g.
  Referral::examinationType: wstepne|okresowe|kontrolne), define a PHP backed
  enum under src/Enum/ (e.g. `enum ExaminationType: string { case Wstepne =
  'wstepne'; ... }`) and map the property as
  `#[ORM\Column(length: 20, enumType: ExaminationType::class)]` with a
  `ExaminationType $examinationType` typed property/getter/setter - Doctrine
  persists the backing string value automatically, no custom DBAL type
  needed. For US-021's input DTO, the equivalent field should be typed as the
  enum itself (or validated with `#[Assert\Choice]` against
  `ExaminationType::cases()` if the DTO field stays a string) so API
  Platform's automatic validation rejects any value outside the 3 enum cases
  with a 422.
- Referral has a `#[ORM\OneToMany(mappedBy: 'referral', targetEntity:
  ReferralExposureFactor::class, cascade: ['persist', 'remove'])]
  $exposureFactors` collection with an `addExposureFactor()` helper that also
  calls `$factor->setReferral($this)` - for US-021's create flow, build each
  ReferralExposureFactor (resolving its `factor` IRI the same way as
  Employee.company) and call `$referral->addExposureFactor($refFactor)`
  before a single `persist($referral)` + `flush()`; cascade persist will
  insert the join rows in the same transaction without persisting each one
  individually.
- `phpdocumentor/reflection-docblock`/`phpstan/phpdoc-parser` are NOT
  installed, so the serializer/PropertyInfo cannot denormalize a JSON array of
  objects into `list<SomeDto>` via a `@var SomeDto[]` doc comment - a DTO
  property meant to receive an array of nested objects (e.g. ReferralInput's
  `exposureFactors: { factor: IRI, exposureDetails: string }[]`) must stay
  typed as plain `array` (each element arrives as an associative array, e.g.
  `$item['factor']`) and be resolved/validated manually in the
  *Service (IriConverter + a thrown
  `Symfony\Component\HttpKernel\Exception\UnprocessableEntityHttpException`
  with a Polish message for an invalid/missing nested `factor` IRI - API
  Platform renders this as a 422 with that message in `detail`, same as the
  409 ConflictHttpException pattern).
- For a DTO field backed by a PHP backed enum's allowed values (e.g.
  ReferralInput::examinationType vs ExaminationType), add a
  `public static function values(): array` to the enum (`array_map(fn($c) =>
  $c->value, self::cases())`) and use
  `#[Assert\Choice(callback: [ExaminationType::class, 'values'], message:
  '...')]` on the DTO string property - keeps the allowed values in one place
  and gives a 422 with `violations[0].propertyPath` on the field for any other
  value.
- To expose a Doctrine OneToMany join-entity collection that itself has no
  #[ApiResource] (e.g. Referral's `exposureFactors: Collection<
  ReferralExposureFactor>`) without a serializer error ("Unable to generate an
  IRI..."), mark the collection property `#[Ignore]` and add a plain-array
  getter (e.g. `getExposureFactorDetails(): array` returning
  `[{factor: id, factorName, exposureDetails}, ...]`) - same
  collection-to-plain-array pattern as ExposureCategory::getFactors().
