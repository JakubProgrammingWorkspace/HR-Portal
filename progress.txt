## Codebase Patterns
- The php container sets `APP_ENV=dev` as a real OS environment variable
  (docker-compose.yml), which takes precedence over phpunit.dist.xml's
  `<server name="APP_ENV" value="test" force="true"/>`. Run tests with
  `docker compose exec -e APP_ENV=test php bin/phpunit` (or
  `bin/console ... --env=test` for console commands against the test DB).
- `php:8.5-fpm` already ships PDO core and Zend OPcache built in — only run
  `docker-php-ext-install pdo_pgsql intl zip` (NOT `pdo` or `opcache`, those
  fail with "cannot stat 'modules/*'" since they have no separate .so to copy).
- backend/ is the Symfony app root (served via nginx from backend/public),
  frontend/ is the Vite/React app root. Both are bind-mounted into their
  containers so host edits are picked up live.
- docker-compose.yml uses `${VAR:-default}` everywhere so the stack works
  out of the box even without a `.env` file; `.env.example` documents all
  overridable vars (DB creds, JWT key paths, CORS origin, ports, app URL).
- frontend/ is a Vite + React 18 + TypeScript app. To add a new frontend
  dependency: edit frontend/package.json, run `docker compose exec node npm
  install`, then `docker run --rm -v "$(pwd)/frontend:/app" alpine chown -R
  1000:1000 /app` to fix root ownership of node_modules/package-lock.json
  before editing with host tools, then `docker compose restart node` to pick
  up the new vite.config.ts/deps. Run `docker compose exec node npm run
  typecheck` (= `tsc --noEmit`) before committing.
- Tailwind CSS v4 is wired via the `@tailwindcss/vite` plugin (in
  vite.config.ts) — no postcss.config/tailwind.config files needed;
  frontend/src/index.css just contains `@import "tailwindcss";`.
- security.yaml `access_control` is first-match-wins: any new path-specific
  rule (e.g. an admin-only attribute backed by a custom Voter) must be listed
  ABOVE the generic `^/api -> IS_AUTHENTICATED_FULLY` catch-all, or it will
  never be reached.
- Voter classes under src/Security/Voter/ extending Symfony's `Voter` are
  auto-registered as `security.voter` services via autoconfigure - no manual
  service tagging needed.
- For entity properties exposed via API Platform where a getter returns a
  different shape than the underlying Doctrine association (e.g. User::$roles
  is `Collection<Role>` but `getRoles(): array<string>` per UserInterface),
  add `#[Ignore]` (Symfony\Component\Serializer\Attribute\Ignore) to the
  property to avoid "Unexpected non-object element in to-many relation"
  normalizer errors; expose the desired shape under a different field name
  if needed.
- API Platform write pattern for entities needing custom field mapping
  (e.g. plain-text password -> hash, role codes -> Role entities): give the
  Post/Patch operation an `input: SomeInput::class` DTO (plain class with
  public properties, optionally `#[Assert\*]` constraints - API Platform
  validates the DTO automatically) and a `processor: SomeProcessor::class`
  implementing `ApiPlatform\State\ProcessorInterface`. The processor calls
  a dedicated `*Service` (thick service / thin processor) that does the
  mapping + EntityManager persist/flush. For Patch, do NOT rely on
  `$context['previous_data']` as the entity to mutate - it is NOT a
  UnitOfWork-managed instance (flush() silently no-ops on it); instead
  re-fetch the entity via its repository using `$uriVariables['id']` inside
  the processor. For business-rule rejections (e.g. "can't delete your own
  account"), throw `Symfony\Component\HttpKernel\Exception\ConflictHttpException`
  with a Polish message - API Platform returns it as a 409 with that message
  in `detail`.
- For DTO field constraints that need a DB lookup (e.g. "code must be
  unique" on a plain input DTO with no Doctrine UniqueEntity support), write
  a custom `Symfony\Component\Validator\Constraint` +
  `ConstraintValidator` pair under src/Validator/ (validator constructor can
  inject a repository directly - validators are services). Apply it as an
  attribute on the DTO property alongside `Assert\NotBlank`/`Assert\Regex`
  etc. API Platform's automatic DTO validation runs all of these together and
  returns a single 422 `ConstraintViolation` response with a `violations`
  array (each entry has `propertyPath` + `message`) - no manual
  ValidationException handling needed in the processor/service.
